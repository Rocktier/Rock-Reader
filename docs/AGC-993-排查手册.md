# AGC 上传报 993「Profile 文件非法」—— 家族排查手册

> 适用范围：Rock 系全部应用（RockReader / Rock私记 / 后续新增）
> 首次成文：2026-10-27（家族已栽 **两次** 993，两次成因完全不同）
> 核心思想：**993 不是玄学，是可判定的**。抠出包内 Profile 看一个字段就能定位。

---

## 0. 一句话结论

> **993 = AGC 认为你包里的 Profile 不可用。**
> 判定只需抠出包内 Profile 看 `type` 字段：
> `debug` ⇒ 用错 product（自动签名）；`release` 但包名不匹配 ⇒ 拿错 Profile；
> **包名也对、证书也有效、验签也过，却还报 993 ⇒ 你传到别的应用栏目下去了**
> （本次真凶）或 **传的是 `unsigned` 包**。

> ⚠️ **最容易被忽略的一条**：包侧全绿时，**错误一定在"包之外"**。
> 本次就是：包完全正确（13 项全过），却传到了「Rock私记」的应用栏目下 ⇒ AGC 拿
> Profile 里的 `com.rocktier.rockreader` 去比对当前应用 `com.rocktier.rockjournal` ⇒ 对不上 ⇒ 993。
> **闸门只能验包，验不了你上传到哪个应用下 —— 这一步只能靠人。**

## 1. AGC 官方对 993 的四条成因

| # | 官方成因 | 怎么查 |
|---|---|---|
| ① | 包内 Profile 已被删除（AGC 后台查不到该 Profile） | AGC 后台「证书/Profile」列表里查 |
| ② | 包内 release Profile 不属于该应用 | 抠包内 Profile 看 `bundle-info.bundle-name`，**再核对 AGC 后台当前上传目标就是这个包名**（本次真凶：传到「Rock私记」栏目下） |
| ③ | Profile 失效（证书被删 / 过期） | 看 Profile 的 `validity.not-after` |
| ④ | **包被自动签名**（用的是调试证书 + 调试 Profile） | 抠包内 Profile 看 `type`，必须是 `release` |

**官方另附两条工程侧成因：**

- `build-profile.json5` 里配了**多个** signingConfig 时，`products[].signingConfig` 必须显式指向**发布签名**；
- 签名写在 `hvigorfile.ts` 的 `overrides` 里**不被认可**，必须写进 `build-profile.json5`。

## 2. 家族两次 993 复盘（成因完全不同，判别方法也不同）

### 第 1 次 · 2026-10-25 · 成因 ④「包被自动签名」

- **现象**：出包上传 AGC → 993。
- **根因**：出包命令写成 `-p product=default` ⇒ 走 DevEco **自动签名**（调试证书 + 调试 Profile）。
  ⇒ 包内 Profile 的 `type` 是 **`debug`**，AGC 直接拒收。
- **认知陷阱**：`buildMode=release` **只管混淆，不管签名**。
  写 `-p buildMode=release` 但 `-p product=default`，照样是调试签名。
- **修法**：出包必须 `-p product=release`（`product` 才决定用哪套签名）。

### 第 2 次 · 2026-10-27 · 成因 ②「传到了别的应用栏目下」（**真凶**）

- **现象**：包侧**逐项全绿**（验签过、Profile `type=release`、包名对、证书有效到 2029、
  与本地 p7b 逐字节一致，闸门 13 项全过），**AGC 仍然报 993**。
- **根因（党哥 22:38 查明）**：**上传时选错了 AGC 后台的应用栏目** ——
  把 Rock阅读 的包传到了**「Rock私记」**的应用下。
  AGC 会拿包内 Profile 的 `bundle-info.bundle-name`（`com.rocktier.rockreader`）
  去比对当前上传目标应用（`com.rocktier.rockjournal`）⇒ 对不上 ⇒ 官方成因②「Profile 不属于该应用」⇒ 993。
  **切到「Rock阅读」栏目重新上传 → 一次通过，已提交审核。**
- **为什么之前会误判成"传了 unsigned 包"**：产物目录里确实有
  `RockReader-release-signed.app` 与 `RockReader-release-unsigned.app` 并排（文件名只差三个字母），
  这**看起来**很像传错文件 ⇒ 曾据此下结论"传的是 unsigned 包"。
  **这个推断是错的** —— 党哥传的就是验过的 signed 包（md5 一致）。
  ⇒ **教训：结构上像的诱因不等于真凶。必须拿到"换了栏目就成功"这种直接证据才能定案。**
- **仍然有效的部分**：signed/unsigned 并排**确实是**每次出包的常态，
  `build-release.ps1` 挑产物的 `-like "*signed*"` 误匹配 `unsigned` **也确实是真 bug**
  （Journal 侧已修）。闸门"文件名含 unsigned 即拒"这条规则也无害，保留。
- **修法**：包侧无需改动（包本来就是对的）。**加一条人工纪律**：
  上传前第一件事是**确认 AGC 后台当前应用是 Rock阅读**（见下方清单第 0 条）。

## 3. 30 秒判别流程（照着做，一次定位）

```powershell
# 1) 从包里抠出 Profile（必须是本地存在的路径，不能写 /tmp）
& "E:\Program Files\Huawei\DevEco Studio\jbr\bin\java" `
  -jar "E:\Program Files\Huawei\DevEco Studio\sdk\default\openharmony\toolchains\lib\hap-sign-tool.jar" `
  verify-app -inFile "<待传包.app>" -inForm zip `
  -outProfile "F:\AI\HarmonyOS\.tmp\out.p7b" -outCertChain "F:\AI\HarmonyOS\.tmp\chain.cer"

# 2) 看 type
#    p7b 是 PKCS#7 容器，JSON 内嵌在二进制里
#    ⇒ 不能用 LastIndexOf("}")，要从第一个 '{' 起做**带字符串感知**的花括号配对
```

抠出 JSON 后按 `type` 分流：

| `type` | 结论 | 动作 |
|---|---|---|
| `debug` | 用错 product（自动签名） | 改用 `-p product=release` 重出包 |
| `release`，但 `bundle-name` ≠ AGC 包名 | 拿错 Profile | 确认 `keys/` 下对应应用的 p7b |
| `release`，包名对，但 `not-after` 已过期 | Profile 失效 | AGC 后台重新生成 Profile |
| `release`，包名对，证书有效，**但 verify-app 说 signature not found** | 传的是 unsigned 包 | 换 `*-signed.app` |
| `release`，包名对，证书有效，**verify-app 全部通过，却仍 993** | **包没问题，错在包之外** | **① 看 AGC 后台当前应用是不是 Rock阅读**（本次真凶）；② 再查 Profile 是否被 AGC 删/失效 |

> **口诀：包侧全绿但仍 993 ⇒ 问题在包之外。**
> 第一嫌疑：**传到了错误的应用栏目下**（AGC 用 Profile 的 bundle-name 比对当前应用）。
> 第二嫌疑：Profile 被 AGC 后台删除/失效（官方成因①③，去后台「证书、App ID 和 Profile」页查）。

## 4. 上传前人工自检清单（8 步，AGC 提交前过一遍）

- [ ] **0. ⭐ 确认 AGC 后台当前应用是「Rock阅读」**（`com.rocktier.rockreader`）——
      **这一步最容易错，也最难被自动化发现**：包本身全对，传错栏目照样 993。
      多应用账号在后台切换栏目时尤其要当心。
- [ ] **1. 文件名不是 `unsigned`** —— 桌面/文件夹里只放**一个**待传包，名字里没有 `un` 前缀
- [ ] **2. 包有签名块** —— `verify-app` 输出 `Digest verify result: true` + `verify-app success`
- [ ] **3. 包内 Profile `type` = `release`**（不是 `debug`）
- [ ] **4. 包内 Profile `bundle-name` = AGC 上的包名**（Rock阅读 = `com.rocktier.rockreader`）
- [ ] **5. 证书未过期**
- [ ] **6. 包内 Profile 与本地 `keys/*.p7b` 的 md5 逐字节一致**（防拿错应用/拿错 Profile）
- [ ] **7. `pack.info` 的 bundleName / versionCode / versionName 正确**，且包内 hap 文件名 = `packages[].name`

## 5. 自动化闸门（**首选，别靠人眼**）

```powershell
# 出包（自动带闸门，不过就 throw，不产出可上传包）
pwsh scripts/build-release.ps1

# 或对已有的包单独跑闸门
pwsh scripts/verify-upload.ps1 -AppPath "C:\Users\Dang\Desktop\Rock阅读-1.0.7-上架.app"
```

闸门逐条覆盖上文清单第 1~7 步，**任何一项不过 → 退出码 1**。
`build-release.ps1` 已把闸门串在出包流程末尾 ⇒ **出包即验收，验收不过就没有"可上传的包"**。

> ⚠️ **闸门的能力边界**：它只能验**包**，验不了「你把包传到了 AGC 的哪个应用下」。
> 本次 993 就是包全对、目标错了 ⇒ **第 0 步（确认当前应用）永远只能靠人**。
> 闸门能做的是：**把包名明确打出来**（`pack.info bundleName = com.rocktier.rockreader`），
> 好让你在 AGC 上传界面能一眼对上。

## 6. 出包铁律（照抄）

```powershell
# ✅ 正确：product 决定签名，buildMode 只管混淆
assembleApp --mode project -p product=release -p buildMode=release --no-daemon

# ❌ 错误一：product=default ⇒ DevEco 自动签名 ⇒ Profile type=debug ⇒ 993
# ❌ 错误二：加了 --mode module ⇒ 报 00306054
# ❌ 错误三：出包后从产物目录「随便挑一个 .app」⇒ 挑到 unsigned ⇒ 993
```

**产物目录里 signed/unsigned 并排是常态** —— 挑包必须靠脚本（已固化在 `build-release.ps1`），
不要靠眼睛。桌面同理：**只留一个待传包**。

**上传铁律**：AGC 后台当前应用 = **Rock阅读**；包名 `com.rocktier.rockreader`。
两应用共用同一张发布证书（rockreader-v2.p12），但各自一张 Profile ⇒ **传错栏目 = Profile 对不上 = 993**。
