## 二、鸿蒙生态三项：接入路径与代价（已查证）

### 2.1 服务卡片 —— ✅ 已落地（1.0.7）

官方路径（API 10+）：DevEco 右键 entry → New → Service Widget → Dynamic Widget，
共包方式生成三件套 `EntryFormAbility.ets` / `WidgetCard.ets` / `form_config.json`。

**Rock阅读的卡片（实际实现，2026-10-29 核对）**：

- **1 张卡、2 种规格**：2×2 + 2×4（`form_config.json:19-23`）
- 2×2：应用名 + 百分比 + 进度条 + 书名 + 作者（`WidgetCard.ets:95-116`）
- 2×4：应用名 + 百分比 + 进度条 + **大号书名** + 作者·章节 + **本章剩余时间**（`:120-146`）
- 整卡点击 = 继续读 → `postCardAction` 带 `params:{bookId}` → `EntryAbility.takeOpenBook()`
  （`EntryAbility.ets:47-61`，含「卡片参数被系统改名 a0/a1」的坑注释）→ 定位 chapter_index + char_offset
- 百分比按**真实字数**算（`bookPercentOf()` `ReadStats.ets:239-276`），不是章数比例
- 推送**双重限流**：内容未变不推 + 同章内 60s 间隔（`CardData.ets:244-272`）
- ⚠️ 「朗读」按钮**刻意没做**（会引入 `KEEP_BACKGROUND_RUNNING`，破坏零权限叙事）—— 与原建议一致

### 2.2 智慧搜索（融合搜索）—— ⬜ 零实现，待拍板

官方机制：索引源应用调 `SearchAbility.insert/update/delete` 建索引，全局搜索（桌面下拉）可搜到；
权限 `ohos.permission.ACCESS_SEARCH_SERVICE`；本机索引用 `DEFAULT_GROUP` 群组（**不经过账号、不联网**）。

**冲突点**：这是 Rock阅读第一个「让数据离开应用进程」的能力——书名/作者会进入系统索引域。
**收缩方案（建议保留）**：
- **只索引书籍元数据**（书名、作者、格式、导入时间），**不索引正文内容**。
  对外叙事可以是「让系统搜到你的书，不搜你读过的内容」——反而比索引正文更符合人设。
- 用户可在设置里关掉（**默认关**，保持零权限口碑，设置里给一行「允许系统全局搜索到我的书籍」）。

**代价**：中。索引同步逻辑（导入/删除书时维护）、权限声明、隐私政策补一段、AGC 应用隐私标签更新。
**实测**：全仓 `SearchAbility|searchAbility` grep = **0 命中**，纯零起步。

### 2.3 小艺建议（意图框架）—— ⬜ 零实现，卡在外部流程

官方流程（Intents Kit）：AGC「开放能力管理」申请意图框架能力（1-3 工作日审核）→ 小艺开放平台
注册意图 → `insight_intent.json` 声明意图 → 应用内 `shareIntent` 共享 → 实现
`InsightIntentExecutor` 处理回调跳落地页。联调要真机 + 开发者选项「意图框架调试」+ 华为账号。

**Rock阅读的适配场景**：「继续读《三体》」习惯推荐卡片——共享的实体只有 bookId + 进度百分比。

**冲突点与判定**：
- 意图共享是**端侧学习**（系统根据习惯在桌面/负一屏出卡）；云侧「个人数据授权（SID）」
  是可选项，**我们不填 = 纯端侧闭环**，符合铁律。
- 但流程上绕不开 AGC 审核 + 真机验证，**实现本身不复杂，卡在外部**。

**行动建议：尽早提交 AGC 能力申请（零成本占位），实现排在其它内功之后。**
**实测**：全仓 `insight_intent|InsightIntent|shareIntent` grep = **0 命中**。

### 2.4 远期牌：HarmonyOS 7 (API 26) 端侧 AI

官方已把「文搜图」做成端侧闭环（Core Vision Kit，本地特征向量 + 本地索引，数据不出端）。
同一范式未来大概率开放文本语义检索。届时「用大白话找书里的一段话」「这本书讲什么」
可以零云端接入。**现在要做的只有一件事：保持全文索引数据结构干净可复用，
不要把它写成只能服务当前 UI 的形状。**（技术预研可等 SDK 开放，现在不投人力。）

### ⚠️ C5 判断修正：「漫画 CBR/CBZ 是低成本空白」不成立

原表说 CBR/CBZ 是低成本空白。实测后**必须拆开**：

- **CBZ 部分低成本**：本质是 zip + 图片序列，`engine/zip/ZipReader.ets` 的 `ZipArchive` 已有
  `names()` / `read()` / `entry()` ⇒ 解析器约 100-150 行，1-2 天。
  ⚠️ 但 ZipReader **不支持 zip64**（`ZipReader.ets:99-101` 抛 `ZIP64_UNSUPPORTED`）⇒ 超大漫画包会失败。
- **CBR 不是低成本**：CBR = **RAR 容器**，不是 zip。HarmonyOS 无现成 RAR 解压 API
  ⇒ 要么引第三方库，要么**只支持 CBZ 并明确告知用户**。
- **真正的���头是渲染侧**：现有 Reader 是**纯文本排版管线**（字符偏移分页 → 行区间→页区间）。
  图片序列的「页」是另一套坐标系，**不能复用** ⇒ 需要独立的翻页/缩放/双页/进度（进度是「第几张图」而非「第几字符」）。
  2000×3000 的漫画页解码后 ~24MB/页，**必须做采样降分辨率，否则 OOM**。

⇒ 结论：CBZ 解析便宜，**漫画阅读模式是大头**，且要一条全新渲染管线。
若要做，建议**只做 CBZ，明确不支持 CBR**。

### 🐛 顺带发现的两个真实缺陷（不在对标范围，但值得修）

1. **MOBI 编码字段解析了但没用** ⇒ UTF-16 / GBK 的 MOBI **解出乱码且不报错**。
   `Mobi.ets:324` 解析出 `encoding = u32(rec0, 28)` 存进 `MobiMeta.encoding`（`:365`），
   但 `MobiParser.ets:96` **无条件用 `utf8Of()`** —— `meta.encoding` 全仓零引用。
   样本恰好全是 UTF-8（`Mobi.ets:18-21` 实测表「编码 65001 UTF-8」）所以没暴露。
   ⇒ 修法：`MobiParser` 按 `meta.encoding` 选 `TextDecoder`（`decodeBytes` 在 `TxtParser.ets:82` 已有）。
2. **MOBI 是唯一没有真实文件回归测试的解析器**：`test/mobi.test.ts` 7 条全是纯逻辑函数级，
   没有一条端到端解析真实 `.mobi`（而 `test/epub.test.ts` / `test/zip.test.ts` 有真实 fixture）。
   ⇒ 补一个 fixture 比补单测函数更能防回归。
