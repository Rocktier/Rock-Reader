# PDF 支持方案（2026-11-05）

> 前提：党哥定的约束 —— **包体积不能变大**；漫画另开应用（本次不考虑 CBZ/CBR）。
> 现状：Reader 1.0.11，`.app` 2331 KB。全仓 PDF 相关代码只有两行注释，无实现。

---

## 一、结论

**用系统 `@kit.PDFKit`，一期只接 `PdfView` 组件。**

- 体积增量 **≈ 0**（系统 kit，不进包；只多出几个调用点）
- 一期可交付：打开、翻页、缩放、单双页、进度续读、页码跳转、关键字搜索、**选中文字**（→ 挂我们自己的摘录）
- 二期再补：PDF 大纲目录、夜间遮罩、双页适配

**不选 pdf.js，不选 PDFium（WASM）。** 理由是体积：它们都要往包里塞 1.5～2.3 MB，等于把包体积翻倍。

---

## 二、先说清 PDF 不是"多支持一种格式"

我们的整条阅读管线建立在**章内字符偏移**上：

```
BookSource.chapterText(chapter) → 字符偏移进度 → 页表 → 书签 → 摘录 → TTS 逐字高亮
```

PDF 是**固定版式**，没有"字符偏移"这个概念，排版设置（字号/行距/字体/护眼主题/简繁转换/净化）**全部不适用**。

所以 PDF 在架构上是**第二套阅读器**：独立页面、独立进度坐标系、独立设置。塞进 `Reader.ets`（2500 行，全是字符偏移逻辑）会互相污染。

参考成熟产品的口径（开源轻页 qingye-reader，HarmonyOS 原生阅读器）在 README 里写得很诚实：

> PDF 原版式阅读：支持文字、扫描和图文 PDF 的目录、缩放、单双页、连续滚动、页码跳转与文字搜索，
> 按物理页保存进度。**暂不支持打开密码、OCR、文字重排、朗读和批注。**

也就是说：**连专门做了 PDF 的成熟产品，也没有做重排/朗读/批注。** 我们的目标应该定在"原版式读得舒服"，而不是"把 PDF 变成 EPUB"。

## 三、三个候选，先把体积摆出来

| 方案 | 体积增量 | 能否在本地模拟器验 | 与现有 UI 融合 | 文字能力 |
|---|---|---|---|---|
| **系统 PDFKit（选定）** | **≈ 0 KB** | ❌ x86 模拟器不行；✅ 云真机（ARM）可以 | 中（组件是黑盒，但可叠遮罩） | 选区文字回调 + 搜索 + 按页取全文 |
| pdf.js（`@ohos/pdfjs` 或自带 worker） | **+1.5～2.3 MB** | ✅ 纯 JS 到处能跑 | 高（自己画） | 最全（有坐标、能重排） |
| PDFium WASM | **+2.1 MB（gzip）/ 4.6 MB 原始** | ✅ | 中 | 无文字层，要自己做 |

判据来源：

- PDF.js 官方 issue 与第三方测量：display 层 minified ≈ 299 KB，display + worker 未压缩 ≈ 1.0～1.5 MB；**中文必须带 cmaps（27 个 bcmap，约 800 KB）**，实际集成 2.1 MB 左右。
- PDFium WASM：EmbedPDF 实测 `pdfium.wasm` 4.63 MB 未压缩 / 2.1 MB gzip，且**固定成本**，没有按需拆分。

**在我们 2.3 MB 的包上，这两条路都是"翻倍级"代价。** PDFKit 是唯一不动体积的选项，而且它已经进了系统，等于华为替我们扛了引擎体积。

代价要认：PDFKit 是 HMS kit（不是 OpenHarmony 开源能力），所以——

1. **CI 会再红一个**（Reader CI 已经因为 `@kit.CoreSpeechKit` 连续红了，见 MEMORY 第七节）。不阻塞发版，但打 tag 也不发 Release。
2. **本地 x86 模拟器跑不了**。但 `compatibleSdkVersion = 5.0.4(16)`，PDFKit 是 `@since 5.0.0(12)`，**版本够**；云调试那台是 ARM 真机（Mate 90），**能验**。
3. 仅中国境内 —— 我们本来就只在国内发。

## 四、可借鉴的项目（看了，但要分会看和不会看）

### 4.1 `Delsin-Yu/JustPDF` —— MIT，最值得读的一个

- HarmonyOS / ArkTS，**`oh-package.json5` 的 `dependencies` 是空的**，零第三方依赖 ⇒ 证实纯系统 PDFKit 就能做完整阅读器。
- 它的架构是**光栅路线**：`workers/PdfRenderWorker.ets`（11 KB）在 Worker 里持有一份 `PdfDocument`，
  用 `page.getCustomPagePixelMap(matrix, false, true)` 渲染成 `PixelMap`，
  `pixelMap.setTransferDetached(true)` 后 `postMessage` 回主线程（跨线程零拷贝转移）。
- 主线程有调度器（`PdfRenderSession`）+ 优先级队列，预渲染邻近页。

**能直接借的**：Worker 持有文档、PixelMap 转移、`maxBitmapPixels` 上限意识（它设 7000 万像素，我们得按屏幕算，见风险节）。

**它反而证明了我们一期的选择更省**：光栅路线要自己写缩放、手势、滚动嵌套（它做了 400+ 行），
而 `PdfView` 组件这些都自带。**光栅留作二期"要夜间模式/要极致"时的备选。**

### 4.2 `wip3l/qingye-reader`（开源轻页）—— ⚠️ GPL-3.0，只读功能边界

- 功能范围是很好的对标样本（见第二节引文），PDF 那一节的取舍（不做密码/OCR/重排/朗读/批注）就是我们的现实边界。
- **许可证是 GPL-3.0**，我们闭源商用**不能抄一行代码**。只能看它"做了什么、不做什么"，实现完全自己写。

### 4.3 `@ohos/pdfjs`（OpenHarmony SIG 移植版）

- 能用，但要背 pdf.js 的完整体积（含 cmaps）。**体积约束下直接排除**，记在这里免得以后有人再提。

## 五、选定方案：一期只接 `PdfView`

### 5.1 用到的两个 API，分工明确

| 阶段 | API | 干什么 |
|---|---|---|
| **导入** | `pdfService.PdfDocument` | `isEncrypted` 判加密、`loadDocument` 验可读、`getPageCount` 拿页数、`getMetadata` 拿标题作者、`getRootBookmarks` 拿大纲、首页 `getPagePixelMap` 生成封面 |
| **阅读** | `PdfView` 组件 + `pdfViewManager.PdfController` | `loadDocument(path, password, initPageIndex)` **直接带初始页**、`getPageIndex` 取当前页、`setPageIndex` 跳页、`searchKey` 搜索、`registerTextSelectedListener` 拿选中文字 |

`TextSelectedParam` 的字段是 `{ text: string; pdfRect: Array<SelectedRects> }`，
`SelectedRects` 继承 `PageRects` 提供 `pageIndex` 与 `rectArray` —— **既有文字又有坐标**，
所以摘录不仅能存文字，还能回原页高亮（`PdfController` 有 UI 层高亮矩形的方法）。

### 5.2 数据模型：**零 schema 改动**

这是这套方案最省的一点。现有 `ReadingProgress` 是 `{ chapterIndex, charOffset, percent }`，
`BookmarkRow` 是 `{ chapterIndex, charOffset, excerpt }`。PDF 直接复用：

| 字段 | PDF 里的含义 |
|---|---|
| `chapterIndex` | **页码**（0 起） |
| `charOffset` | 恒为 0 |
| `percent` | `(页 + 1) / 总页数` |
| `excerpt` | 该页 `getTextContent()` 前 60 字 |

⇒ `chapter` 表、`progress` 表、`bookmark` 表、书架进度条、继续阅读，**全部不用改**。

### 5.3 新增/改动清单（**已按此落地**，实际行数以文件为准）

| 文件 | 性质 | 状态 |
|---|---|---|
| `engine/pdf/PdfPages.ets` | **新建，纯逻辑**（页号↔进度换算、页码标签、跳页输入解析、书名过滤） | ✅ 完成，**node 单测 30 条** |
| `engine/pdf/PdfProbe.ets` | 新建（导入期调 pdfService 探文件；`canIUse` 能力探测） | ✅ 完成 |
| `pages/PdfReader.ets` | **新建页面**（组件 + 跳页 + 搜索 + 进度 + 时长统计） | ✅ 完成 |
| `engine/importer/BookImporter.ets` | 改：`parseKindOf` 加 `pdf`、导入分支、PDF 大小上限单独放宽 | ✅ 完成 |
| `engine/importer/ImportReason.ets` | 改：加密 / 损坏 / 设备不支持 三条文案 | ✅ 完成 |
| `pages/Index.ets` | 改：书架点击 **一个分支**（`routeTo`）跳 `PdfReader` | ✅ 完成 |
| `engine/parser/BookSource.ets` | 不改（PDF 不走 `chapterText`） | ✅ 0 改动 |

⚠️ 两处与最初估的不一样，记录下来免得下次又估错：

1. 文件名是 **`PdfProbe.ets`** 而不是 `PdfMeta.ets` —— 它做的事是"探一次文件能不能开"，
   不是"读元数据"，名字跟职责走。
2. **没有 `BackStack` 改动**。PDF 页只有两层浮层（跳页 / 搜索），
   直接 `onBackPress` 里就地判断即可，不必拉进 `BackStack` 那套层级枚举
   （那个是给 Reader 的五层浮层准备的，PDF 套上去是过度设计）。

### 5.4 界面（实际做的）

- 顶栏：返回 + 书名 + `12 / 240`（1 基显示，转换只发生在 `pageLabel` 一处）
- 底部栏：页码 + **搜索** + **跳页**
- 跳页面板：支持 `12` / `12/340` / `65%` 三种写法，输错只提示不跳
- 搜索面板：`searchKey` 由组件高亮全文命中，面板只管"上一个/下一个"计数
- 系统返回键：先收浮动面板，再退出页面
- ⚠️ **夜间遮罩没做**（原计划要做）：等党哥定"PDF 保持原色还是叠遮罩"。
  现在深色主题下 PDF 仍是白底 —— 这是**已知的观感缺口**，不是 bug。

## 六、分期

| 期 | 内容 | 验收 |
|---|---|---|
| **一期** ✅ | 导入 + 打开 + 连续滚动 + 缩放（组件手势）+ 进度续读 + 页码跳页 + 搜索 | ⬜ **待真机验**：打开一本 200 页 PDF，翻到中间退出，重进回到原页 |
| 二期 | 大纲目录（`getRootBookmarks`）、选中文字→摘录→回页高亮、夜间遮罩、书架封面 | 云真机：选中一句存摘录，回原页能看到高亮 |
| 三期（可选） | 光栅路线替换 PdfView，换取完全的视觉统一 | 仅在二期发现组件体验不可接受时启动 |

**一期不做**（明确写死，防止范围蔓延）：PDF 密码解锁、OCR、文字重排、朗读、批注编辑、PDF 内链跳转。

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **本地模拟器验不了**（x86 不支持 PDFKit） | 开发期看不到效果，反馈慢 | 样本 PDF 打进 `rawfile/`，用**云调试**（ARM 真机）跑；与 all2md 的 PDF 验收同一套路 |
| 大页面内存爆 | 白屏/闪退 | 一期用 `PdfView` 由系统管内存，风险低；若走光栅，**单页像素上限按屏幕算**（1080×2400×2 屏 ≈ 10 M px ≈ 40 MB），绝不能照抄 JustPDF 的 7000 万 |
| CI 再红一个 | 打 tag 不发 Release | 已知，不阻塞（MEMORY 第七节口径）。不为它改 CI |
| 扫描件 PDF 无文字 | 搜索/目录为空，用户以为坏了 | `getTextContent()` 为空时**明确提示**"这是扫描件，只能看不能搜" |
| 组件手势与我们的菜单冲突 | 点中央呼不出菜单 | 一期就用 `PdfNestedScrollOptions` + 边缘手势验证；不行则在四角加隐形热区 |
| 体积失控 | 违背约束 | **出包体积闸门**：`.hap` 比上一版大超过 200 KB 就停手查原因（预期只多几 KB） |

## 八、验证路径（不开本地模拟器也能推）

1. **纯逻辑先测**：`PdfPages.ets` 用 node 单测（页号换算、边界、大纲扁平化），不依赖 PDFKit。
2. **编译验签名**：`assembleHap` 能过 = `@kit.PDFKit` 的类型与当前 SDK 匹配。
3. **真数据喂内核**：把一份真实 PDF 的"页数 / 大纲 / 每页文字"导出成 JSON 固件，喂给纯逻辑层跑。
4. **云真机验端到端**：样本 PDF 放 `rawfile/`，应用启动时复制进沙箱（`BookImporter` 已有"从 rawfile 导入"的同类逻辑，all2md 那边也是这么做的）。
5. **包内核对**：出包后 grep `modules.abc` 里的 `loadDocument` / `PdfView` 字符串，证明真的编进去了（沿用 1.0.10 那次的手法）。

## 九、党哥的答复（2026-11-05）与据此的定论

> 「阅读类的应用所涉及的 PDF，一般就是论文或者是电子书文档」

这句话把三个问题一次答完，且**排除了最坏的一种情况**（扫描版）：

1. **都是文字版** ⇒ 有文字层 ⇒ **搜索可用、文字可选**（二期摘录才成立）。
   不需要 OCR，也不需要"这是扫描件只能看不能搜"的提示。
2. **默认「适应宽度」**（`PageFit.FIT_WIDTH`）。论文常双栏，适应页面会把正文缩到看不清；
   电子书单栏适应宽度正好铺满。
3. **不做密码解锁**（一期）：加密 PDF 在导入时就拒掉，用户看到的是
   「这本 PDF 有密码，暂时打不开」，而不是点进去一片空白。

剩下两个我按最小可实现面自己定了，如不合意随时改：

- **一期范围**：能读、能翻、能搜、能续读、能跳页。不含摘录与大纲（那是二期）。
- **PDF 夜间显示**：暂时**保持原色**（不加遮罩）。多数阅读器也这么做，
  而且 PDF 上盖半透明黑会让图表发灰、论文里的灰度标注看不清。
