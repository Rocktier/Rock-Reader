## 二、模拟器造书：导入通道全被封死后的唯一出路

三条路全死（都不是产品 bug，是系统限制）：
1. `aa start -U file://...` → AMS `[permission_verification.cpp121] verify fail`，**静默剥离 want.uri**；
2. 隐式 `viewData` 带 uri → 「暂无可用打开方式」（module.json5 注释矩阵：带 uri 的一律不命中）；
3. `/storage/media/**` → SELinux 只读，shell 写不进，文件选择器也看不见。

**破局的关键工具是 sqlite3 的 `writefile()`**（不是 `hdc file send`，它被 SELinux 拦）：

| 手段 | 能写哪里 |
|---|---|
| `hdc file send` | 只到 `/data/local/tmp` |
| shell `cat >` | 只到 `/storage/media` 之外的 777 目录（bundle 根 `files/`） |
| shell `mkdir` | **一律被拒**（没有 add_dir 权限） |
| **sqlite3 `writefile()`** | **应用私有目录也行**（含 `haps/entry/files`）—— 权限比 cat 高 |

完整配方（已固化成 `scripts/seed-sim-book.mjs`）：
```bash
# 1) 本地：用产品自己的 splitChapters 切章，生成两份 SQL
node scripts/seed-sim-book.mjs probe.txt "进度测试书" "验证组" b_sim01
# 2) 把书本体送进应用沙箱（writefile + 十六进制字面量）
hdc file send write.sql /data/local/tmp/write.sql
hdc shell "cat /data/local/tmp/write.sql | sqlite3 :memory:"
# 3) 执行 books/chapters 的 INSERT
hdc shell "cat /data/local/tmp/seed.sql | sqlite3 <db路径>"
# 4) books.path 用**应用视角**路径：/data/storage/el2/base/haps/entry/files/probe.txt
```

**五个必须记住的细节**：
- `sqlite3 <db> < file` **不生效**（只执行第一行）；必须 `cat file | sqlite3 <db>`。
- `readfile()` 在这台设备的 sqlite3 build 里**没编**（返回 NULL）；`writefile()` 可用。
- 大 blob 用管道传 SQL 文件（452KB 一次成功）；走命令行传 64KB hex 会被 Windows 拒绝（Argument list too long）。
- **shell 与应用是两套 mount 视图**：shell 看不到 `/data/storage/**`；应用也看不到 `/data/app/**`。books.path 必须写应用视角路径。
- 写库前先 `aa force-stop` 应用 + 删 `-wal/-shm/-dwr/-compare` 残件。

## 三、⚠️ ArkUI V1 的分支条件陷阱（家族级，本次最重要的发现）

**症状**：搜索框输入后书确实被过滤掉了（ForEach 数据源重新求值了），但「没搜到」的空态**永远不出现**。

**根因**：ArkUI V1 是「状态变更 → 局部刷新」，**build() 不会整体重跑**；
`if (条件)` 的**分支条件按首次求值定型**。而依赖插桩只认「表达式里直接读 @State」——
条件写成 `if (this.searchedEmpty)`（getter）或 `if (this.someMethod())`，插桩**追不到 getter/方法体里的 @State 访问**，
于是 ArkUI 不知道这个分支依赖 query，条件永远不变 ⇒ 永远走错分支。

**正解**：**条件里就地读 @State**
```ts
if (this.query.length > 0 && this.visibleItems().length === 0) { ... }
```
**@Computed 救不了**：编译报 `The '@Computed' decorator can only be used in a 'struct' decorated with '@ComponentV2'`（本项目是 V1 组件）。

**判据（下次遇到「数据变了 UI 不更新」时按序查）**：
1. ForEach 的 key 少带了变化的那一位？（家族老坑第 N 次）
2. **分支条件是不是藏在 getter/方法里？**（本次命中）
3. 组件高度是不是被 layoutWeight 压成 0？（本次也命中，见下）

## 四、根 Column 高度：两个空态其实一直是隐形的

`layoutWeight(1)` 分的是「父容器的剩余空间」，父容器高度不确定时剩余空间是 **0** ⇒ 空态被压成 0 高度、文案不可见。
根 `Stack { Column { … } }` 里 Column 没写高度 ⇒ 根 Column 补 `.width('100%').height('100%')` 才让 layoutWeight 拿到空间。
（本次靠「删掉书 → 另一个空态分支『书在你手上，哪儿也不去』能正常显示」定性出是高度问题，不是分支没进。）
