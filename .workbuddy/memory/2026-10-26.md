### 进度口径 bug（党哥发现的，数据证实）
- 旧算法 `(chapterIndex+pagePercent)/chapterCount` —— 假设每章一样长。
  实测《暗恋·橘生淮南》100 章 39.3 万字，读到第7章 2/3：**显示 8.67%，真实只有 4.66%**。
- 根因更深：`engine/epub/EpubParse.ets` 里 `startChar/endChar` **硬编码 0**，
  EPUB 导入只读目录不读正文 → chapters 表 100 行 start_char/end_char **全 0**，拿不到各章字数。
- 修了一版（代码就位）：chapters 加 `char_count` 列 + 迁移；`bookPercentOf()` 纯函数放
  `engine/stats/ReadStats.ets`；Reader 展开某章时回填该章字数，打开书后台 `surveyChars()` 普查。
- **⚠️ 未生效待修**：普查触发链路本轮没跑起来，装机实测 char_count 仍是全 None，
  percent 仍走旧口径（等于没变差，不影响 1.0.6 发出）。下一轮优先查：
  surveyChars 是否被调用（怀疑 init 的 `if (this.areaReady)` 分支不是真正开书路径，
  实际走的是约 518 行的 `openChapter(this.chapterIndex, keep)`）、以及 saveChapterCharCount 的 UPDATE。
- ⚠️ 教训：光靠「已读章均值」外推救不了长度不均的书 —— 本例前9章均值 2093 字 vs
  全书均值 3928 字，外推出来 8.75%，跟按章数的 8.67% 一样虚高。**必须做全量普查**。

### 其它修复/结论
- **卡片推送 bug（我引入的）**：节流顺序是「先写快照 → 再判断推不推」，命中限流时快照已到 9
  卡片还停在 8，且很可能就是用户离开阅读页的最后一次进展再也补不上。
  修：`pushCardUpdate(ctx, force)`，`persistProgress(force)` 的最后一击穿透限流。
- **B2 智慧搜索做不了**：`ohos.permission.ACCESS_SEARCH_SERVICE` 在 SDK permissions.d.ts 里存在，
  但配套索引 API 不在公开 SDK（只给系统应用）。三方 App 无法写系统全局搜索 → 划掉。

### 出包陷阱（这次踩的）
- **versionName 忘了 bump**：1.0.5 上架时是 code 1000006/name 1.0.5，本轮差点直接出同名包
  → 上传会因版本未变被拒。1.0.6 = code **1000007** / name **1.0.6**。每次出包必查 AppScope/app.json5。
- **verify-app 工具失效**：`app_check_tool.jar verify-app -inFile ... -inForm zip` 现在报
  9132101 全部参数 invalid（工具版本变了）。替代验证（更快更实）：
  `hdc uninstall` + `hdc install <app>` —— 装得上就是签名/Profile 有效。
- 拆 pack.info 看版本/模块注册：`zipfile → pack.info → summary.app.version`。
