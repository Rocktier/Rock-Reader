### 4.1 Rock阅读 —— 划词「加入摘录」（全链路打通）

**先纠正昨天记错的一条**：「`onTextSelectionChange` / `editMenuOptions` 都是 API 26 起、本工程 20 用不了」——**错的**。
查 SDK 26 `component/text_common.d.ts` 实测：`onTextSelectionChange` **@since 11**、`textSelectable` **@since 12**、
`editMenuOptions` **@since 12**；只有 `SelectionContainer` **组件本身** @since 26 ⇒ **不用升 compileSdk**。

**四个真坑（按踩到顺序）**：

1. **`.gesture(LongPressGesture())` 挂在正文 Text 上 ⇒ 系统长按选词完全不出现**
   （截图无手柄无菜单、UI 树 0 个 TextMenu 节点）—— 自定义手势**抢赢**了 Text 自带的长按选词。
   ⇒ **长按必须完整让给系统**，摘录面板改由「加入摘录」菜单项唤起。
2. **选区只选中 1 个字**（中文长按默认粒度）⇒ 之前「少于 2 字就丢弃」的门槛把用户点击变成**死路**
   （点了「加入摘录」毫无反应）。⇒ 门槛降级成「要不要提示用户选区偏短」，**进面板只看空不空**。
3. **`onMenuItemClick` 返回 `true`（完全拦截系统默认逻辑）⇒ 系统浮动菜单留在屏幕上**，
   浮在我们自己的面板上面。⇒ **返回 `false`**（我们的逻辑先跑，系统默认逻辑照跑 ⇒ 收起菜单）。
4. **残留选区手柄撤不掉**：compileSdk 20 的 `UIContext` **没有** `clearFocus`（API 26 才有），
   切 `textSelectable` 也**撤不掉已建立的选区**。⇒ 正解：
   `Text(content, { controller })` + `TextController.setTextSelection(0, 0)` + `closeSelectionMenu()`。
   ⚠️ 残留手柄会**压在抽屉页签上**（正文左上角），点页签反而重新弹系统菜单 ⇒ 页签点不动。

**最终交互**：长按正文 → 系统选区（可拖手柄扩选）→ 菜单「加入摘录」（在 ⌄ 溢出菜单里）
→ 我们的摘录面板**预填精确选中的那句**（可选色 + 写注 + 可编辑）→ 存下 → 标记页签可见。
整页快照的老路径降级为中央菜单里的「摘录」按钮。

## 6. 新项目：all2md（家族第 9 个应用）—— 规划 + 设计稿

党哥新开项目 `F:/AI/HarmonyOS/all2md`：**AI first，为 AI 提供粮食**。
把手机上杂乱的文件转成 Markdown + 一个对标 Typora 的阅读器。参照 `microsoft/markitdown`。

### 6.1 调研结论（已查证，别再重查）

**许可证**（`gh api repos/<r> .license.spdx_id`）：
- markitdown **MIT**（19.4 万 star）· docling **MIT** · marker **Apache-2.0** · mammoth.js **BSD-2**
  · turndown **MIT** · markdown-it **MIT**
- ⚠️ **pandoc = GPL-2.0**（传染性）⇒ 闭源商业应用**一行都不能碰**，只对标它的格式矩阵
- ⚠️ Typora 闭源商业 ⇒ 只对标交互，不碰代码与主题

**鸿蒙能力**：
- PDF 文本抽取 = `pdfService.PdfPage.getTextContent()`，**API 23（6.1.0）才有**
  （早期只有渲染没有抽取）⇒ **新工程起步就定 compileSdk ≥ 23**
- Reader Kit（`@kit.ReaderKit`）能解 TXT/EPUB/MOBI/AZW/AZW3，**API 16 起，不支持模拟器**
- OCR = `@kit.CoreVisionKit` textRecognition（端侧，中/英/日/韩/繁，给 block→line 结构）
- ❌ **DOCX/XLSX/PPTX 无官方解析能力**（OOXML 要自己解 zip+XML）
- ❌ **Markdown 无官方渲染组件**（要自研原生渲染器）
⇒ 这两项「无官方」= 项目 80% 工作量

**markitdown 的定位**：README 明说不做桌面/移动应用；且自认「输出给 LLM 够用，
**不适合需要高保真的人读**」⇒ 我们的差异化正好是「人眼质检台 + 端侧离线」。

### 6.2 我拍定的三条架构律

① **统一 AST，不做点对点**（MacFarlane/Pandoc 的教训；markitdown 是每格式各拼字符串）
② **除 `platform/` 外不 import `@kit.*`** ⇒ 内核纯逻辑可 node 单测（家族强项）
③ **宁可丢样式不能丢结构**（Willison：结构是 LLM 的骨架）

### 6.3 头号技术风险（写进规划 4.3）

**PDF 转 MD 的真问题不是「抽字」，是「重排段落」**：
`getTextContent()` 只给带 `\r\n` 的一维字符串，没有字号没有坐标 ⇒
- 一视觉行 = 一行文本 ⇒ 一段被切成 5 行 ⇒ 必须做段落合并（行尾非终止标点就并）
- **拿不到标题层级**，只能启发式推断 ⇒ 产品层面如实标注「推断的」
- 表格在文本流里是空格堆 ⇒ **宁可不生成表，也不生成假表**（假表对 AI 危害更大）

### 6.4 设计稿（`all2md/docs/ui-mockup-v1.html`）

六屏：转换台空态 / 转换中（加载+失败）/ 阅读器渲染态 / 大纲全屏页 / 体检报告 / 源码轻修。

### 7.2 ⭐ build-profile 版本字段的两个坑（新知识）

1. **`runtimeOS: HarmonyOS` 时 compatibleSdkVersion / targetSdkVersion 必须是字符串**，

2. **`targetSdkVersion: "26.0.0(26)"` 会报 `00308018 api version parameter is illegal`** ——
   因为 26 这一代的 API 号**本身就是三段式 `26.0.0`**（不像 6.1.0 → `23`）。
   ⇒ 正确写法是**不带括号**的 `"26.0.0"`。
3. **版本名↔API 号的权威映射表**（以后不用猜）：
   `DevEco Studio/tools/hvigor/hvigor-ohos-plugin/node_modules/@ohos/hos-sdkmanager-common/build/res/hos-config.json`

### 7.4 ⭐ 六条「测试逼出来的」真 bug（都是领域知识，不是笔误）

1. **列表项会把后面整段正文吞进自己** —— 因为 PDF 文本没有空行，列表项之后的普通段落
   被当成续行。修法：**上一行以句末标点结尾 ⇒ 该项结束**。
2. **`- 12 -` 这种页码会被 `- ` 规则吃成列表项** ⇒ A5 永远查不到页码。
   修法：**页码判断必须排在列表判断之前**，单独成段落块。
3. **中文单空格不能无脑删** —— `第二条 结算周期` 删成 `第二条结算周期` 就变另一个词了。
   修法：默认路径只压连续空格（`normalizeSpaces`）；`collapseInnerSpaces`（删中文间空格）
   只留给 PDF 读入器，因为只有它知道自己面对的是「逐字排版空格」。
4. **有序列表转义吞掉后续空格**：`i += len + 1` 多算一格 ⇒ `1. 不是列表` 变 `1\.不是列表`。
5. **表格分隔行比数据行短** ⇒ 源文本参差不齐。四个对齐分支都要按 `width+2` 构造。
6. **`（1）总则` 全角括号不识别** ⇒ 全角括号后通常无空格，必须与半角 `1. ` 分开写正则
   （半角 `.` `)` 要求 `\s+`，否则 `1.5 米` 会误判）。

## 8. all2md DOCX 读入器（2026-11-03 22:20）

党哥发话出包后留到下次的活，这一轮先做「不依赖签名」的部分：**DOCX 读入器**。
理由：DOCX 的标题来自 `w:pStyle`，结构是**作者声明的**，比 PDF 靠猜可靠得多；
且解 zip 有 `@ohos.zlib`、解 XML 有 `@ohos.xml`，是纯工程活。PDF 放它后面。

### 8.1 新增文件（`all2md/entry/src/main/ets/core/read/office/`）

- `XmlLite.ets` —— **手写 XML 词法器**（元素 / 属性 / 文本 / 自闭合 / 注释 / CDATA /
  五类命名实体 + 数字实体 + 代理对）。
  ⭐ **不用 `@ohos.xml` 的唯一理由：内核必须能在 node 里跑** ——
  DOCX 转换的正确性只能靠单测保证（模拟器里没法逐段核对一份 200 行的合同）。
- `DocxReader.ets`（903 行）—— `document.xml` → 统一 AST。

### 8.2 ⭐ DOCX 的领域知识（以后不用再查规范）

| 位置 | 事实 | 坑 |
|---|---|---|
| 标题 | `w:pStyle` 的 val 可能是 `Heading1` / `标题 1` / `1`..`9` / `Title` | 中文版 Word 与 WPS 写法都不同，要正则兜住 |
| 标题兜底 | `w:outlineLvl` val **0–8 有效，9 = 正文文本** | 9 当标题会凭空多出一堆 h |
| 加粗 | `<w:b/>` = 开，但 **`<w:b w:val="0"/>` = 显式取消** | 只判存在性会把取消加粗的地方加粗 |
| 列表 | `w:numId="0"` = **显式取消编号**，不是列表项 | 当列表处理会凭空多一层 |
| 列表有序性 | 要查 `numbering.xml`：numId → abstractNumId → lvl/@numFmt | `bullet` = 无序，其余有序 |
| 合并单元格 | `w:gridSpan` 横跨 N 列、`w:vMerge`（无 val = 延续） | GFM **没有合并语法**，必须降级 |
| 图片 alt | `wp:docPr@descr` | 取不到**就留空**，让 A4 报，不编假描述 |
| 修订 | `w:ins` 保留、`w:del` 丢弃 | 丢 `w:del` 才是读者看到的版本 |
| 域代码 | `w:instrText` 丢弃、域结果保留 | 不丢会输出 `PAGE \* MERGEFORMAT` 混进正文 |
| 内容控件 | `w:sdt`/`w:sdtContent` **必须进去** | 封面、目录全被 sdt 包着，不进等于丢内容 |

**合并单元格降级的判据（这条是产品立场）**：横跨 N 列 ⇒ 第一格放内容、后 N-1 格填空；
纵向延续 ⇒ 留空。得到的结果**行列数与视觉网格一致**（结构不丢），只是合并格内容
只出现在左上角。**反过来「按视觉补全内容」更糟** —— AI 会读到重复信息。

### 8.3 ⭐⭐ ArkTS 的三个新坑（都是编译期才炸，单测抓不到）

1. **`null` 与 `undefined` 是两种类型，`x === undefined` 挡不住 `null`。**
   `firstChild()` 返回 `null`，而查询函数只声明 `XmlNode | undefined` ⇒
   运行到 `node.attrs` 直接 `TypeError`，**23 条单测一起红**。
   ⇒ 函数签名写成 `XmlNode | null | undefined`，判空写成 `x === null || x === undefined`。
2. **非空断言 `!` 不允许**，而且**自己写的 `isAbsent()` 不是类型守卫**（TS/ArkTS 都不据此收窄）
   ⇒ 不能用「先判空、后面用 `!`」，只能**内联判断**让类型自然收窄。
3. **`arr[k].field !== undefined ? arr[k].field : ''` 收窄失效** ⇒ 报
   `Type 'string | undefined' is not assignable to type 'string'`
   ⇒ **必须先取到局部变量** `const x = arr[k];` 再判。

### 8.4 测试逼出来的两个真缺陷

1. **只含图片、没有文字的段落会产出一个空段落块** —— Word 里插图独占一段极常见，
   空段落块会让 A7 判「有空段落」Fail，**真正的问题（图片没 alt）反被假警报盖住**。
   修法：`inlines.length === 0` 时不产出段落块，只产出图片块。
2. 8.3 第 1 条（null vs undefined）本身也是被测试逼出来的。
