## 1. 两应用对标梳理 + Markdown 双向落地

党哥：「两个日记和阅读应用，距离最优秀的项目还有什么可以做的？我暂时不打开模拟器，你先从代码角度实现。」

### 先诊断，再动手（两处判断都被代码推翻）

- **Reader 的「每日目标」不是缺口** —— 以为要新做，`ReaderPrefs` 里早有
  `DAILY_GOAL_STEPS [0,10,20,30,60]` + 默认 20 + `nextDailyGoal()` 循环切档（注释标 "A4"）。
  **教训：动手前先 grep 一遍，别凭"标杆有、我们大概没有"就写。**
- **Reader 整体已不是功能荒**：全文搜索 / 书签 / 摘录 / 目录 / 主题 / 翻页 / 亮度 6 档 /
  常亮 / 字体族 / 简繁 / 去广告 / TTS（音色+语速）/ 自动滚动 / 统计（连续·成就·本章与全书剩余）/
  每日目标 / 每本书独立排版，**全都在**。
  真正硬的缺口是 **EPUB 插图**（`Reader.ets` 里图片相关命中几乎为零 ⇒ 书里的图读不出来），
  但那要解压取图 + 落沙箱 + 渲染，**必须看效果** ⇒ 与"不开模拟器"冲突，留给能开的时候。

### 做的是什么：Journal 的 Markdown 双向（A 类待办④）

原来只能**导出** MD（`BackupService.toMarkdown`），不能读回来 ——
数据"能拿走"却"放不回来"，"数据永远属于你"只兑现一半。

新增 `entry/src/main/ets/data/MarkdownImport.ets`（纯逻辑，零 `@kit`，node 可测）+ Settings 入口。

**五条设计判据**（都是踩过/差点踩的）：

1. ⭐ **宁可把标记当文字，也不能丢一个字。** 未配对的 `*` 原样保留；解析不了的行一律落成段落。
   日记应用丢字是灾难，排版难看只是难看。
2. ⭐ **严格 UTF-8 解码，不用宽松版。** `BackupService.utf8Decode` 遇到非法字节会拼成乱码
   而**不报错** —— GBK 文件导进来就是满屏乱码，且已经写进库了。
   `decodeUtf8Strict` 遇到非法序列返回空串 ⇒ 界面直接说"不是 UTF-8，请另存"。
3. **剥 BOM。** 记事本另存必然带 `\uFEFF`，不剥则首行 `## 日期` 认不出（整篇会退化成一篇）。
4. **落库走 `importAll`（→`planImport`）**，不逐篇 `saveEntry`：
   索引只落盘一次（逐篇是 O(N²)，几百篇会卡死）、id 撞号自动换新、正文写失败有回滚。
5. **重复只告知、不跳过。** 判据 = 同日期 + 同 preview。同一天写两篇开头一样的日记是合法的，
   自动跳过等于替用户删掉第二篇 ⇒ 宁可提示"其中 N 篇与已有内容相同"。

**格式对应**（与导出严格对齐，因此能做 round-trip）：
`## YYYY-MM-DD` 分篇 / `### ` 标题 / `- ``* ``+ ``1. ` 列表 / `**粗**`·`*斜*`·`***粗斜***` /
`> 心情：😄 开心` 反查心情 id / `[图片]` 计数后跳过。

**验证**：单测 **293/293**（原 253 + 40 条），ArkTS debug 编译通过。
测试里有价值的三条：
- **round-trip 连行内样式一起验**（导出→导入后 bold/italic/both 都还原）—— 这才叫"双向"
- GBK 字节必须被拒 / 截断序列 / 过长编码 `C0 80`
- `a * b` 里的星号是乘号，不该变斜体

提交：RockJournal `8cb54ae`。

## 3. PDF 方案调研（党哥：体积不能大；漫画另做应用）

**先纠正一个认知**：PDF 读不了**不是模拟器的问题**。全仓 `pdf` 只命中 `MarkupParser` 里两行注释，
`parseKindOf('pdf')` 返回空串 ⇒ 导入时直接 `NOT_SUPPORTED`。**真机上一样读不了。**

**三个候选的体积（决定性判据）**：
- 系统 `@kit.PDFKit` ⇒ **≈ 0 KB**（系统 kit 不进包）
- pdf.js（`@ohos/pdfjs`）⇒ **+1.5~2.3 MB**（中文必须带 27 个 bcmap ≈ 800 KB；display+worker 未压缩 1.0~1.5 MB）
- PDFium WASM ⇒ **+4.63 MB 原始 / 2.1 MB gzip**，且是固定成本、不可按需拆

我们包现在 2331 KB ⇒ 后两条都是**翻倍级**。**体积约束下只有一个选项。**

**GitHub 上真正值得看的两个**：
- `Delsin-Yu/JustPDF`（MIT）—— `oh-package.json5` 的 `dependencies` **是空的** ⇒ 证明纯系统 PDFKit 就能做完整阅读器。
  架构是光栅路线：Worker 持 `PdfDocument` → `page.getCustomPagePixelMap(matrix,false,true)` → `pixelMap.setTransferDetached(true)` → postMessage 零拷贝转移。
  主线程有调度器与优先级队列。⚠️ 它设 `maxBitmapPixels = 7000 万`（≈280 MB）——**我们绝不能照抄**，按屏幕算（1080×2400×2 ≈ 10 M px ≈ 40 MB）。
- `wip3l/qingye-reader`（**GPL-3.0**）—— 功能边界极好的对标样本，但它 PDF 那节的口径才是重点：
  「支持文字/扫描/图文 PDF 的目录、缩放、单双页、连续滚动、页码跳转与文字搜索，按物理页存进度；
  **暂不支持打开密码、OCR、文字重排、朗读和批注**」⇒ **连专门做 PDF 的产品也没做重排/朗读/批注**。
  ⚠️ GPL 代码一行都不能抄，只看"做什么、不做什么"。

**选型：一期只接 `PdfView` 组件**（不是光栅）。理由：组件自带缩放/滚动/单双页/搜索/**文字选区**，
光栅要自己写 400+ 行手势还不一定有选区。光栅留作二期备选。

**API 关键事实（本地 SDK 核实，非文档二手）**：
- 导入用 `pdfService.PdfDocument`：`isEncrypted(path)`、`loadDocument(path,password)`→`ParseResult`、
  `getPageCount()`、`getMetadata()`、`getRootBookmarks()`、`getPage(i).getPagePixelMap()`（做封面）
- 阅读用 `pdfViewManager.PdfController`：`loadDocument(path,password,initPageIndex)` **能直接带初始页**（续读极省事）、
  `getPageIndex()`、`searchKey(text,listener)`、
  `registerTextSelectedListener` 回调 `TextSelectedParam { text, pdfRect: SelectedRects[] }` ⇒ **既有文字又有坐标，能回原页高亮**
- `PdfView` 组件属性：`controller` / `pageLayout` / `isContinuous` / `showScroll` / `pageFit`
- 版本：`@since 5.0.0(12)`，我们 `compatibleSdkVersion 5.0.4(16)` ⇒ **够**

**最省的一点：零 schema 改动。** `ReadingProgress{chapterIndex,charOffset,percent}` 与 `BookmarkRow` 直接复用 ——
`chapterIndex` = 页码、`charOffset` = 0、`percent` = (页+1)/总页。章表/进度表/书签表/书架进度条全不用动。

**为什么不塞进 `Reader.ets`**：整条管线吃"章内字符偏移"，PDF 是固定版式，塞进去互相污染 ⇒ 独立 `PdfReader.ets`，
书架点击加**一个分支**。

方案全文 ⇒ `docs/PDF支持方案-2026-11-05.md`（含分期、风险表、验证路径、明确不做的清单）。

**验证路径的关键结论**：本地 x86 模拟器跑不了 PDFKit，但**云调试那台是 ARM 真机 ⇒ 能验**。
样本 PDF 打进 `rawfile/`（all2md 同一套路），不依赖灌文件。

## 4. PDF 一期落地（党哥：我们的 PDF 就是论文和电子书）

党哥原话：「阅读类的应用所涉及的 PDF，一般就是论文或者是电子书文档」。

**这一句答完了三个问题，并排除了最坏情况**：论文与电子书都是**有文字层**的
⇒ 搜索可用、文字可选（二期摘录才成立）；不需要 OCR；不需要"这是扫描件只能看不能搜"。

据此定的三条：

- 默认 `PageFit.FIT_WIDTH`（论文双栏必须；电子书也正好铺满）
- 不做密码解锁：加密 PDF **导入时就拒**，用户看到的是「这本 PDF 有密码」，
  而不是点进去一片空白
- PDF 夜间**保持原色**（不加遮罩）：大多数阅读器也这么做，而且盖半透明黑会让
  论文的图表、灰度标注失真

**新增 4 个文件**

| 文件 | 职责 |
|---|---|
| `engine/pdf/PdfPages.ets` | **纯逻辑**：页码↔进度、夹紧、页签文案、跳页输入解析、书名过滤。零 @kit ⇒ node 可测 |
| `engine/pdf/PdfProbe.ets` | 薄壳：`canIUse` 能力探测 + `PdfDocument.loadDocument` 探文件 + release |
| `pages/PdfReader.ets` | 阅读页：PdfView + 顶栏 + 底栏（页码/搜索/跳页）+ 进度 + 时长 |
| `test/pdfpages.test.ts` | 30 条 |

**改 3 处**：`BookImporter`（parseKindOf 加 pdf、导入分支、PDF 大小上限单独放宽到 300MB）、
`ImportReason`（加密/损坏/设备不支持三条文案）、`Index.ets`（`routeTo` 单点分流）。

**零 schema 改动**：`chapterIndex` 直接当页码、`charOffset` 恒 0、`percent` 由页码算。
进度表 / 书签表 / 书架进度条 / `listAllProgress()` 全没动。

**几个动手时才发现的判断**

- ⭐ **分母必须用 `total - 1`**：若用 `(page+1)/total`，3 页的论文一打开就显示
  「读过 33%」——书架看着像已经读过了。单测专门锁这条。
- ⭐ **`clampPage` 挡 NaN**：`total=0`（还没 load 完）时任何除法都会产 NaN，
  写进库就再也画不出进度条，**不可逆脏数据**。
- **书名不能直接用 metadata**：论文 PDF 的 `title` 多半是
  `Microsoft Word - 论文初稿.doc`（导出软件塞的），比文件名更糟。
  `pickPdfTitle` 过滤软件默认前缀后退回文件名。
- **导入期必须探一次**：加密 / 下载到一半的 PDF 能拷进沙箱、能进书架，却永远打不开。
  探失败 ⇒ **不进书架 + 删沙箱副本**（不留孤儿文件）。
- **`canIUse` 单独成一个原因 `PDF_UNSUPPORTED`**：本地 x86 模拟器就是这条。
  不能混进「文件损坏」—— 前者换设备就能读，后者会让人去重新下载文件。

**ArkTS 两个编译坑（都是当场红的）**

1. `getParams()` 不能 `params['bookId']` 索引访问（`arkts-no-props-by-index`）
   ⇒ 定义 `interface PdfReaderParams { bookId: string }` 再 `as`（Reader.ets 同写法）。
2. `BookDb` 没有 `instance()` 单例 ⇒ `new BookDb()` + `db.open(ctx)`（幂等）。
   `ReaderPrefs` 同理，且主题要 `effectiveTheme(bookId)`（这本书覆盖优先）
   —— PDF 页不能另立一套规则，否则同一本书的文字版和 PDF 版会一深一浅。

**验证**：单测 **337/337**（原 307 + 30）；ArkTS debug 编译通过。
⚠️ **真机一次都没验过**：本地模拟器 `canIUse` 为 false，PDFKit 根本不可用。

**最该先验的一条（写在这里免得忘）**：我按「先 `controller.loadDocument`，再渲染
`PdfView`」实现（控制器独立于视图，官方示例也是这个顺序）。若真机上出现
**底栏页码正常但中间一片白**，就是这个顺序不被接受 ⇒ 改成
「先渲染 PdfView，在其 `onAppear` 里 load」。这个假设只有真机能证伪。
